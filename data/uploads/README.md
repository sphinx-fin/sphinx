# data/uploads (소유: 정세현)

업로드된 상품문서(F-EXT-001 · 이슈 #521)가 사는 곳. **여기 있는 파일은 git 에 안 들어간다**
— 이 README 만 추적한다.

## ❗빈 디렉토리를 커밋해 두는 이유 — 지우면 ai-service 가 기동하지 않는다

배포에서 실제 파일은 호스트 트리가 아니라 **이름 있는 도커 볼륨**(`sphinx_uploads`)에 산다.
호스트 트리가 배포마다 새 디렉토리라(`mktemp -d -p /opt`) 거기 쓴 업로드는 다음 배포에서
사라지기 때문이다. 커밋된 원본 2종은 git 이 매 회차 다시 가져오지만 업로드본은 아무도
다시 만들어 주지 않는다.

그런데 `ai-service` 는 `./data:/data:ro` 로 `data/` 를 **읽기 전용**으로 통째 마운트하고,
그 위에 `/data/uploads` 를 겹쳐 붙인다. Docker 는 마운트 지점이 없으면 **만들려고 하는데
부모가 읽기 전용이라 실패하고, 컨테이너가 아예 뜨지 않는다.**

```
실측:
  data/uploads 없음  →  error mounting … create mountpoint for /data/uploads:
                        read-only file system            ← ai-service 기동 실패
  data/uploads 있음  →  /data/timeseries/VERSION(고정 코퍼스) · /data/uploads/…(업로드본)
                        둘 다 읽힌다
                        /data/uploads 쓰기는 거부된다     ← 의도대로
```

즉 이 디렉토리는 **호스트에 있어야 하는 빈 마운트 지점**이다. 볼륨이 그 위에 덮이므로
배포에서는 안이 보이지 않는다.

## 고정 코퍼스와 섞이지 않는다

같은 `data/` 아래 있지만 성격이 다르다. `timeseries/`·`documents/` 는 `VERSION` 의
sha256 으로 고정한 재현성의 입력이고(결정 7.8 · P2), 여기는 사람이 올린 것이다. 배포에서
둘이 **다른 저장소에 산다** — 앞의 것은 git 트리, 이쪽은 도커 볼륨. 그래서 고정 코퍼스의
sha256 이 덮는 범위가 이것 때문에 흔들리지 않는다.

## 왜 `/data` 밖으로 빼지 않았나

`ai-service` 가 문서를 읽어도 되는 뿌리가 `SPHINX_DATA_DIR` 하나이고
(`parsing.py` `documents_root()`), `resolve_document_path` 가 그 밖의 경로를 파일을
만지기 전에 거부한다. 밖으로 빼면 그 방어를 고쳐야 하는데, 같은 함수의 주석이
*"전용 환경변수를 새로 만들지 않는다 — 결정 전에 knob 을 박으면 결정이 그 knob 에
맞춰진다"* 로 그것을 이미 막아 두었다. 안에 두면 `document_path` 가
`uploads/<sha256>.pdf` 로 `documents/…` 와 같은 문법이 되고 계약이 하나도 안 바뀐다.

## 레이아웃은 `uploads/<sha256>/<정제한 파일명>`

디렉토리가 내용 주소(sha256)이고 **파일명은 올린 것을 정제해서 살린다.** 경로 결정에서
이름을 뺀 것이 요점이라, 파일명이 경로를 정하지 않는다.

처음에 `<sha256>.pdf` 로 제안했다가 되돌렸다(`#527` 리뷰 교차). **결정적인 것은 이 볼륨이
복구 수단이 없는 유일한 자산이라는 사실이다** — `external: true` 를 고른 것과 같은 근거인데,
같은 사실이 파일명에도 걸린다. DB 를 잃고 볼륨만 남은 상황에서 `9f2a….pdf` 만 있는 트리는
**어느 파일이 무엇인지 아무도 모른다.** 「무엇을 올렸는가」가 볼륨 안에 남아야 한다.

### ❗되돌리면서 약해진 것 둘 — 「그대로 성립한다」고 적었다가 정정한다 (PR #532 리뷰 ⑤)

해시가 **파일명**이던 안에서는 셋이 다 성립했는데, 디렉토리로 올리면서 둘이 반쪽이 됐다.

```
같은 PDF 를 두 이름으로 올리면
  uploads/9f2a…/설명서.pdf
  uploads/9f2a…/pamphlet.pdf     ← 같은 바이트가 두 벌
```

1. **경로 조작 차단 — 그대로 성립한다.** 디렉토리가 해시라 업로더가 준 이름은 경로 결정에
   관여하지 않는다. 이건 배치가 바뀌어도 안 흔들린다.
2. **재업로드 dedup — 반쪽이다.** 같은 내용이 한 디렉토리에 모이는 것까지가 참이고,
   **파일은 이름마다 한 벌씩 생긴다.** 게다가 상품ID 가 파일명 슬러그를 쓰므로
   (`doc-<슬러그>-<sha256 앞 8자>`) 같은 문서를 다른 이름으로 올리면 **다른 상품**이 된다.
   진짜 dedup 은 쓰는 쪽이 해시 디렉토리를 먼저 나열해야 하고, 그 동작은 명세도 구현도 없다.
3. **무결성 대조 — 방향이 한쪽만이다.** 경로가 그 파일 내용의 해시를 *주장*하므로 대조할
   기준이 경로에 있다(내용을 다시 해싱해 맞춰볼 수 있다). 반대 방향은 안 된다 — **해시만으로
   파일을 지목할 수 없고** 조회가 둘을 만날 수 있다.

**2·3 을 불변식으로 놓고 코드를 쓰지 않는다.** 필요해지면 그때 「같은 해시에 파일 하나」를
쓰는 쪽에서 강제해야 하고, 그것은 이 문서가 약속할 수 있는 것이 아니다.

## ❗쓰는 것은 server 하나이고, 볼륨 소유자가 걸린다

`server` 컨테이너는 비루트(uid 10001, gid 10001)로 돈다. `docker volume create` 는 볼륨
루트를 `root:root` 로 만들므로 그대로 두면 **업로드가 EACCES 로 500** 이다.

**소유권은 배포 스크립트가 멱등하게 맞춘다.**

```
deploy_ec2.sh   docker volume create --label … sphinx_uploads
                docker run --rm -v sphinx_uploads:/v busybox chown 10001:10001 /v
```

이미지에 굽지 않는 이유는 `server/Dockerfile` 주석에 있다 — 요지는 **Docker 의 copy-up 이
빈 볼륨에만 도는 일회성 부작용**이라, 한 번 root 소유로 굳으면 그 뒤로는 영원히 no-op 이고
배포가 그것에 대해 아무 말도 안 한다는 것이다. 손으로 고쳐야 할 상황이 되면 같은 명령이다.

```
docker run --rm -v sphinx_uploads:/v busybox chown -R 10001:10001 /v
```

gid 를 `Dockerfile` 에서 `groupadd --gid 10001` 로 못 박아 뒀다 — 안 그러면 베이스 이미지가
고른 값(temurin 에서는 999)이 되고, 위 명령이 베이스가 바뀌는 날 조용히 틀려진다.

`ai-service` 는 같은 지점을 `:ro` 로 붙어서 읽기만 한다 — 파서가 자기 입력을 고칠 수
있으면 재현성(P2)의 전제가 깨진다.

## 경로 방어는 아직 반쪽이다 (PR #532 리뷰 ⑥)

이 문서가 「이중 방어」로 인용했던 두 층의 실제 상태다.

```
safeFilename                    ❗이 브랜치에 없다 — #527 이 넣는다
ProductDocuments.resolveWithin   normalize() + startsWith 라 심볼릭 링크를 안 따진다
```

짝인 파이썬 쪽은 `.resolve()` 로 끝까지 풀고 그 이유까지 적어 뒀다 —
`parsing.resolve_document_path` 의 *"심볼릭 링크로 밖을 가리키는 것도 막아야 해서"*.
**`uploads/` 는 `/data` 아래 첫 「사람 행동으로 내용이 정해지는」 트리**라, 이 비대칭이
여기서부터 이론이 아니다. 자바 쪽을 `toRealPath()` 계열로 맞추는 것은 제가(정세현) 뗀다.
