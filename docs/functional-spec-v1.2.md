## 0. 시스템 개요

### 0.1 한 줄 정의

금융상품 계약 직전, 고객이 상품을 자기 말로 설명하게 하고(되말하기), AI가 항목별 이해도를 채점하여, 룰 엔진이 판매 진행 여부를 신호등으로 판정하는 이해도 검증 게이트.

### 0.2 설계 원칙 (전 모듈 공통 제약) — 그리고 어디가 강제하는가

v1.1의 여섯 원칙은 그대로다. v1.2는 **각 원칙이 코드 어디에서 강제되는지**를 같이 적는다 — 원칙이 문서에만 있으면 심사에서 확인할 수 없다.

| # | 원칙 | 구현 제약 | 강제 지점 (레포) |
| --- | --- | --- | --- |
| P1 | AI는 측정, 룰은 결정 | LLM 출력이 직접 게이트 판정·금액 계산에 쓰이면 안 된다. LLM 출력 → 구조화 데이터 → 룰 엔진의 단방향 흐름만 허용 | `domain/Judgment`(측정값) ↔ `core/gate/GateEngine` + `gate_rules.yaml`(판정) 분리. 게이트 입력은 등급·신뢰도·모순 여부의 구조화 값만 |
| P2 | 숫자는 결정론 | 손실 시뮬레이션·금액 환산은 순수 함수로 구현. 동일 입력 = 동일 출력 (재현성 100%) | `simulator/` 순수 함수 · `data/timeseries/VERSION` 이 지수 CSV 의 sha256 을 고정 · 재현성 단위 테스트 |
| P3 | 개인정보는 LLM 이전에 제거 | PII 마스킹은 룰 기반 전처리에서 수행. LLM 프롬프트에 PII 도달 금지 | 고객 텍스트가 ai-service 로 나가는 **단일 경로** `core/pii/PiiGateway` → `core/aiservice/AiServiceClient`. ai-service 는 입구(`PiiGuardMiddleware`)에서 재검사. 세션 생성 스키마에 성명·주민번호 필드가 **존재하지 않는다** |
| P4 | 판정에는 근거 첨부 의무 | 모든 채점·오해 탐지 결과는 근거(고객 발화 인용 + 루브릭 조항)를 반드시 포함. 근거 없는 판정은 시스템 오류 | `Judgment` 생성자가 근거 누락을 거부 → `EVIDENCE_REQUIRED`(502). ai-service `verify_quote_is_verbatim`(인용이 발화 원문에 있는가) · `verify_rubric_clause_is_published`(인용 조항이 공개 루브릭 파일에 있는가) |
| P5 | 오판 비대칭 보수 처리 | 신뢰도가 임계값 미만이면 황색(재검증)으로 강등. 미탐(오해→이해) 최소화가 오탐 최소화보다 우선 | `gate_rules.yaml` **R-00**(미측정 항목 있으면 RED) · R-01(U4 → RED)이 R-05(저신뢰 → YELLOW)보다 **앞에** 있어 저신뢰 U4 는 RED 로 남는다 · 오해 라이브러리 매칭은 등급을 U4 로 **고정**(`apply_misconception_floor`) · 평가 리포트가 미탐율을 카파와 **따로** 낸다 |
| P6 | 상품 수치는 원문 인용만 | 재설명·추출의 상품 조건값은 원문 복사만 허용. LLM 의 수치 생성 차단 | `RiskItem.condition.value_text` 는 `pages[page].text[start:end]` 와 **글자가 같아야** 한다(항등식 테스트) · 재설명 생성 후 수치 대조 · 추출이 원문에 없는 수치를 내면 항목 반려 |

### 0.3 시스템 구성도 — 실제 배치

```
  브라우저 ──https──▶ web (nginx + React/Vite)            ← 외부에 열린 것은 이것 하나 (:80/:443)
                        │  /api → server:8000  (접두어 /api 를 벗겨 전달)
                        ▼
                     server (Spring Boot 3.3 · Java 17)     ← 상태머신 · 게이트 · PII 경계 · 불변 기록 · 권한
                        │  http://ai-service:8100/internal/*   (내부망 전용 · 브라우저 도달 불가)
                        ▼
                     ai-service (FastAPI · Python 3.12)     ← 파싱 · 추출 · 질문 · 채점 · 오해 · 모순 · 재설명
                        │
                     LLM (gpt-5-mini 단일 모델 정책 · reasoning_effort=minimal)

  DB   로컬·테스트 H2 인메모리 / 배포 MySQL 8.4 (Flyway validate)
```

v1.1 의 M1~M6 모듈 구분은 아래 절 번호로 그대로 유지한다. **데이터가 흐르는 방향이 곧 보안 경계**다 — 고객 텍스트는 server 의 PII 경계를 지나야만 ai-service 에 닿고, ai-service 는 `ports:` 없이 내부 네트워크에만 있다.

### 0.4 사용자 역할 — 그리고 «없는» 역할

| 역할 | 코드 | 권한 (실제 `rbac_policy.yaml` action) |
| --- | --- | --- |
| 고객 | CUST | `report:summary:read`(own_session) — **대면 채널에서는 도달 불가**(인증 주체가 판매자 단말 하나라서. 이유는 결정 로그 10.72). MOBILE 채널 착수 전 |
| 판매 직원 | SELLER | `session:create/read/interview/answer/judge/simulate` · `session:judgment:read` · `report:read/issue` · `override:request` · `product:read` — **전부 `own_session`**(자기가 진행한 세션만) |
| 관리자(지점) | MGR | `session:read` · `session:judgment:read` · `report:read` · `override:approve` · `aggregate:*` — **전부 `branch`**(자기 지점만) |
| 컴플라이언스 | COMPL | 위 읽기 전부 + `audit:read/verify` · `aggregate:*` · `signal:unfair:read` — `org`(전체) |
| 시스템 관리자 | ADMIN | `product:manage` · `admin:role:assign` — `org`. 승인 산출물(루브릭)은 git 커밋이 정본이므로 **쓰기 그랜트가 없다** |

**의도적으로 없는 역할** — `rbac_policy.yaml` 의 `absent_by_design` 에 문면으로 적혀 있다:

> 본부 영업·마케팅 — 집계된 이해도 데이터는 "설득하기 쉬운 고객" 목록이 될 수 있다. 이를 소비할 수 있는 유일한 주체이므로 **역할 자체를 만들지 않는다** (ADR-001, 기획서 7-4).

권한을 안 주는 것과 줄 대상이 없는 것은 운영 압박이 들어왔을 때 다르게 작동한다 — 역할이 없으면 부여하려면 코드를 고쳐야 하고 PR 에 남는다. `Role` enum 에 값을 추가하는 변경은 ADR-001 재검토 대상이다. **역할만으로는 부족하다**는 것도 정책 파일이 강제한다 — 같은 action 에 역할마다 데이터 범위(`own_session` / `branch` / `org`)가 붙는다.

### 0.5 핵심 상태 정의

**이해도 4단계 (항목 단위)** — v1.1 과 같다.

| 코드 | 명칭 | 정의 | 게이트 매핑 |
| --- | --- | --- | --- |
| U1 | 이해 | 루브릭 필수 요소를 자기 말로 재현 (`u1_requires` 개 이상) | 녹색 |
| U2 | 부분이해 | 필수 요소 일부 누락, 오류는 없음 | 황색 |
| U3 | 미이해 | "모르겠다" 또는 무관한 답변 | 황색 |
| U4 | 오해 | 사실과 다른 내용을 사실로 진술 | 적색 |

**신호등 3색 (세션 단위) — 실제 룰셋 `gate_rules.yaml` v5.** 위에서 아래로 **첫 번째 참인 룰**이 판정을 정하고, 발화한 룰 ID 가 `ruleTrace` 로 기록된다. 룰 순서가 곧 P5 의 구현이다.

| 룰 | 조건 | 신호 | 사람이 보는 문면 |
| --- | --- | --- | --- |
| R-00 | `unmeasured > 0` (채점되지 않은 항목이 있다) | RED | 채점되지 않은 항목이 있습니다 |
| R-01 | `anyGrade == 'U4'` | RED | 오해가 확인된 항목이 있습니다 |
| R-02 | `suitabilityMismatch == true` | RED | 설명 내용과 투자성향이 어긋납니다 |
| R-03 | `reverifyFailed >= 2` | RED | 재검증을 반복했지만 이해가 확인되지 않았습니다 |
| R-04 | `anyGrade in ['U2','U3']` | YELLOW | 이해가 확인되지 않은 항목이 있습니다 |
| R-02b | `suitabilityUnknown == true` (모순 판정을 **못 했다**) | YELLOW | 투자성향을 확인할 수 없습니다 |
| R-07 | `repeatedAnswerUpgraded > 0` (재설명 뒤 같은 말 반복) | YELLOW | 재설명 뒤에도 같은 설명이 반복되었습니다 |
| R-05 | `anyConfidenceBelow 0.7` | YELLOW | 판정 신뢰도가 낮은 항목이 있습니다 |
| R-06 | `allGrade == 'U1'` | GREEN | 모든 항목의 이해가 확인되었습니다 |

v1.1 대비 추가된 룰 셋: **R-00**(측정 안 된 것을 «없음»으로 세지 않는다 — 추출 실패 required 항목이 있으면 그 상품의 모든 세션이 RED), **R-02b**(모순을 «없음»과 «확인 못 함»으로 가른다), **R-07**(재설명이 이해로 이어졌는지를 문면 반복으로 잡는다). 세 룰은 전부 *"침묵이 정상으로 읽히는 자리를 문면으로 가른다"* 는 같은 판단에서 나왔다.

**세션 상태 머신** — `CREATED → IN_PROGRESS → (RE_EXPLAIN ⇄ RE_VERIFY)* → JUDGED → CLOSED / ABORTED`. 불법 전이는 `ILLEGAL_STATE_TRANSITION`(409)로 거부한다.

## 1. M1. 위험요소 자동 추출 엔진

### F-EXT-001 상품문서 업로드 및 파싱

| 항목 | 내용 |
| --- | --- |
| 설명 | 공시 PDF(ELS 간이투자설명서 · 변액 상품요약서/운용설명서)를 텍스트·표로 구조화한다 |
| 입력 | PDF, 상품유형(`ELS` / `VARIABLE_INSURANCE`) |
| 출력 | `ParsedDocument` — 쪽 단위 원문(`pages[].text`) · 표 · 파싱 경고 · `parser_version`(현재 **0.3.0**) |
| 처리 | `pdfplumber` 텍스트 레이어 추출 → 표 안은 **칸 순서**로 읽고, 같은 y 로 합쳐 온 칸은 도로 가른다(문장 중간에서 끊기던 인용을 고친 자리 — 이슈 #436·#452·#455) |
| 예외 | 암호화·손상 PDF 는 파서 예외를 422 로 낸다. **스캔 이미지 페이지는 OCR 하지 않고 「텍스트 없음」으로 노출한다**(은폐하지 않는다) |
| 수용 기준 | 데모 대상 2종에서 필수 항목이 위치 참조와 함께 파싱됨 — alpha 실측: ELS 16쪽 · 변액 18쪽 |
| **v1.1 대비** | ① **OCR 폴백 미구현** — 데모 문서 2종이 텍스트 레이어를 갖고 있어 범위에서 뺐다. ② **`POST /products/documents` 실배선**(이슈 #521) — 올린 파일을 저장하고 상품ID(`doc-<파일명 슬러그>-<sha256 앞 16자>`, 슬러그가 비면 `doc-<sha256 앞 16자>`)를 발급한 뒤 파싱한다. 파일은 배포에서 이름 있는 도커 볼륨(`sphinx_uploads`)에 살고 ai-service 가 같은 뿌리를 읽기로 붙는다. 문서를 못 연 경우는 200 + `parse_failed`(ai-service 장애 502 와 가른다). 사전 탑재 공시 문서 2종은 **폴백으로 남는다** — 키 없는 환경에서 데모가 계속 돌아야 한다(걷는 것은 #403). 문서 원문은 `GET /products/{id}/document` 로 화면에서 열 수 있다. 업로드 **화면**(S-01)의 실패 큐 노출은 아직 남았다(결정 10.40 · 이슈 #406) |

### F-EXT-002 필수 이해항목 추출 (LLM)

| 항목 | 내용 |
| --- | --- |
| 설명 | 파싱된 문서에서 상품유형 템플릿의 이해항목과 조건값을 추출한다 |
| 입력 | `ParsedDocument`, 상품유형 템플릿(`ai-service/app/templates/*.yaml`) |
| 출력 | `RiskItem[]` — {`itemId`, `name`, `importance`(required / recommended), `condition`{`valueText`, `sourceSpan`{page,start,end}}, `status`(extracted / extraction_failed), `failureReason`} |
| 템플릿 (MVP 고정) | **ELS 13항목**(required 10): 예금자보호 비대상 · 원금손실 가능성 · 조기상환 조건 · 낙인 배리어 · 만기 손실조건 · 전액손실 사례 · 과거 데이터 모의실험 · 중도상환 원금손실 · 환금성 제약(비상장) · 발행사 신용위험 + recommended 3(고난도상품 · 고령자 숙려제도 · 숙려기간) · **변액보험 10항목**(required 7): 실적배당형 성격 · 원금손실 가능성 · 예금자보호 범위 · 월공제액 차감 구조 · 은행 저축과 다름 · 해약환급금 < 납입보험료 · 조기해지 환급률 + recommended 3 |
| 통제 (P6) | 조건값은 원문 스팬을 동반하고 `pages[page].text[start:end] == valueText` 항등식이 테스트로 잠긴다. 원문에 없는 수치는 항목 반려. 구조화 출력에 `strict` 스키마 강제(이슈 #490) |
| 예외 | E-EXT-03 — 항목을 비우지 않고 `extraction_failed` 로 생성. **required 항목이 하나라도 실패하면 그 상품의 모든 새 세션이 R-00 으로 RED**(이슈 #463) — 누락이 조용히 통과로 새지 않는다 |
| 수용 기준 | alpha 실측(2026-09-06): ELS 13/13 추출 · required 10/10 · 변액 10/10 · required 7/7 |
| **v1.1 대비** | 템플릿이 ELS 6 → **13**, 변액 5 → **10** 항목으로 늘었고 `importance` 가 붙었다(근거: 결정 10.1 — 항목마다 공시 근거를 요구). `item_id` 정본은 계약 샘플의 긴 형식(ADR-006). 각 항목의 채점 기준(**루브릭 17종**)은 `ai-service/app/rubrics/*.yaml` 파일이 정본이고 `u1_requires`(몇 개를 말해야 U1 인가)를 문면으로 든다 — ELS 10종 확정, 변액 7종 초안 |

### F-EXT-003 추출 결과 검증 (공시문서 대조)

| 항목 | 내용 |
| --- | --- |
| 설명 | 자동 추출 항목을 정답 세트와 대조해 재현율을 산출한다 |
| 입력 | `RiskItem[]`, 정답 세트 = 계약 샘플의 `_expected_risk_items`(ELS 13 · 변액 10) |

## 7. 공통 기능

### F-CMN-001 PII 마스킹 전처리

정규식 5종을 **순서대로**(EMAIL → RRN → CARD → PHONE → ACCOUNT — 일반 패턴이 앞엣것을 삼키지 않게) 적용하는 `PiiGateway` 를 `AiServiceClient` 안에 두어 **어떤 모듈도 우회해서 LLM 을 부를 수 없다.** 마스킹 전에 NFC 정규화(결정 10.2.1). 원문은 남기지 않고 **종류별 건수만** 계량한다(`PiiMeter` — 마스킹이 동작했다는 증거가 코드 주석이 아니라 숫자). ai-service 도 입구에서 재검사한다 — 공시 문서 경로는 넓은 휴리스틱(계좌·카드)을 끄고 좁은 패턴(주민번호·전화)만 보며, **어느 경로가 완화 대상인지를 요청 스키마에서 유도해 테스트가 잠근다.** 마스킹 실패 감지 시 ai-service 가 422 로 거부한다.

**v1.1 대비** — 「성명 사전」은 미구현(대면 채널은 판매자 입력이라 발화에 성명이 들어올 자리가 없다). 「관리자 알림」은 계량 지표로 대체.

### F-CMN-002 접근 통제·감사 로그

`rbac_policy.yaml` 이 **권한의 유일한 근거**다 — 20개 action 에 역할과 데이터 범위(`own_session`/`branch`/`org`)가 붙고, 컨트롤러는 action 이름만 참조한다. Java 상수로 중복 정의하지 않는다. 미정의 action 은 기본 거부. **12개 action 은 감사 대상**(`audited`) — 판정·발행·승인·집계·시뮬레이터 열람·상품 등록 등 「누가 무엇을 봤는지」가 남아야 하는 것. 감사 로그는 `AuditInterceptor` 단일 통로로 리포트와 **같은 불변 기반**에 쌓이고, `GET /dashboard/audit-summary`(action·결과코드·**역할별 차단 건수**) · `audit-verify`(체인 재계산)로 COMPL 이 본다.

**강제 조건** — `sphinx.security.enforce=true` 는 `prod` 프로파일에서만 켜진다. 배포(compose)는 그 프로파일로 뜬다. 데모 개방 모드(심사위원 무로그인 관람)에서는 nginx 가 경로별로 데모 계정을 주입하므로 **개방 모드와 역할 차단 시연은 배타적**이다 — 차단은 nginx 를 지나지 않는 경로(서버 컨테이너 직접 호출)로 보인다.

**v1.1 대비** — 정책이 파일 실물이 됐고, «없는 역할»이 정책 파일 문면(`absent_by_design`)에 적혔다. 접근 통제와 감사 로그가 F-GTE-004 와 기반을 공유한다(ADR-003).

### F-CMN-003 채점 성능 측정 파이프라인

`eval/` — 표본(`corpus`) · 고정 문맥(`context`, 파서 판 기록) · 2인 라벨(`labels`) · 모델 출력(`model.jsonl`, 프롬프트 판·문맥 판 기록)을 읽어 리포트를 낸다. 입력이 없으면 0 이 아니라 **비영점으로 죽는다**. 문맥이 파서 판과 어긋나면 · 모델 출력이 문맥 판과 어긋나면 **CI 가 문다**(이슈 #409·#477·#480).

**이번 회차 결과 (2026-09-06 · [상세](eval-report.md))**

| 지표 | 값 | 비고 |
| --- | --- | --- |
| 표본 | ELS 70발화 · 10항목 · 라벨러 2인(강희진·정세현) 독립 | 프롬프트 당사자(윤지석) 제외 |
| 상한(라벨러 간) | QWK **+0.769** · 일치율 72.9% | 사람도 안 맞는 항목에서 모델이 맞기를 기대할 수 없다 |
| 모델 ↔ 합의(51건) | QWK **+0.828** · 일치율 80.4% | **기획 5절 목표 +0.75 달성** |
| 모델 ↔ 각 라벨러(70건) | +0.694 / +0.723 | 상한의 90% / 94% |
| 미탐 U4 → U1 | **0 / 19** | 게이트가 GREEN 까지 갈 수 있는 경로(R-06) — 없다 |
| 미탐 U4 → U2·U3 | 4 / 19 = 21.1% | RED 가 YELLOW 로 내려앉는 경로(R-04) — 재설명이 걸리므로 차단은 아니다 |

기획 5절의 「오해→이해 오판율 1% 이하」는 **U4→U1 로 읽으면 0%(달성), U4→U2·U3 까지 넓게 읽으면 21.1%(미달)**다. 리포트는 둘을 갈라 적고 어느 정의로 잰 수치인지를 문면에 박는다. 수치에 붙는 단서(한 항목의 문맥 인용이 루브릭 요소를 반쪽만 덮는다 · 한 항목에서 두 라벨러가 갈린다)도 리포트 0절에 있다 — **숫자만 떼어 인용하지 않는다.**

**v1.1 대비** — 「항목당 30발화 · 합성 100건」→ 실제 70발화 · 2인. 라벨러가 운영자(정세현)를 포함해 **평가자·피평가자 분리가 완전하지 않다** — 그 한계와 되돌리는 조건은 `eval/labeling/guideline.md` §5 에 있다.

## 12. 한계와 고도화 — 실측이 가리키는 다음 칸 (2026-09-06 기준)

이 절만 **아직 없는 것**을 다룬다. 1~11절의 기능 표에는 구현된 것만 있고, 여기 적힌 것은 하나도 그 표에 섞여 있지 않다. 각 행은 *"하고 싶다"* 가 아니라 **3주 구현 중 어디서 재서 나온 다음 칸인가**를 근거로 든다 — 근거 없는 행은 넣지 않았다. 시장·채널 확장(음성·TM·GA·B2G·상품 확대)은 기획서 §11의 몫이라 여기 반복하지 않는다.

v1.1의 미결정 5건은 전부 답이 났다 — ① 음성 제외 ② 신뢰도 임계 0.7은 게이트 파일이 소유(ADR-005) ③ 원문 보존 6개월(기본 꺼짐) ④ 데모 수치 확정(4절 표) ⑤ 룰셋·루브릭·라이브러리는 **git(파일)이 정본**, DB에 두지 않는다(런타임 기준을 쓰면 P4 검증이 순환).

### 12.3 하지 않기로 한 것 — 이유와 함께

| 무엇 | 왜 안 하나 |
| --- | --- |
| 인지 기능 변화(취약 신호) 감지 | **별도 동의 체계가 선행**돼야 한다 — v1.1 §11부터 의도적 제외 |
| LLM 출력을 게이트 판정에 직접 넣는 것 (예: 대필 의심 점수) | P1 — 측정과 결정의 경계. `inputMeta`는 수집하되 게이트·화면에 안 넣는다(결정 6.4) |
| 루브릭·룰셋·라이브러리를 DB로 옮기는 것 | P4 — 채점이 런타임 생성 기준을 쓰면 `verify_rubric_clause_is_published`가 순환한다. 승인은 git 커밋 |
| 불변 기록의 `type: "override"` 등 식별자 개명 | append-only — 이미 굳은 해시 체인 안의 값. 화면 문면만 「예외 승인」으로 바꾼다 |
| 개별 세션에 «코칭 의심» 표시 | 기획 7-4 2단계는 **집계 이상 탐지**다 — 개인 단위 표시는 그 원칙을 깨고 판매자 반발만 산다 |
| 음성 입력·TM·GA·B2G·상품 확대 | 기획서 §11 확장 목록 — 이 명세의 범위가 아니다 |
