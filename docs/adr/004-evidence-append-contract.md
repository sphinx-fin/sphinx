# ADR-004. `evidence` 적재는 세션 트랜잭션에 묶고, 중복을 흡수하지 않는다

- **상태**: Accepted
- **일자**: 2026-08-25
- **결정자**: 정세현 / 협의: 강희진
- **관련**: F-GTE-004, F-CMN-002, F-GTE-001, [ADR-003](003-evidence-ownership.md), [ADR-005](005-threshold-ownership.md), PR #16, PR #28, 이슈 #39

## 맥락

ADR-003 이 `evidence` 공통 기반의 **소유**를 정했지만 **적재 규약**은 비어 있었다. F-INT-004
재검증 루프(PR #28)를 붙이면서 세 가지가 실제 문제가 됐다.

1. `Session` 이 판정과 게이트 결과를 **덮어쓴다**. `recordJudgment` 주석이 *"재검증 시 덮어씀"*
   이고 `recordGate` 도 세션 단일 필드다. 그러면 기획서 174행이 이해 기록의 3요소 중 하나로
   못박은 **재설명 이력**이 복원 불가능해진다. 하필 7-2 [기능 1](황색 → 재설명 → 녹색)이 그
   경로 자체다
2. `EvidenceRecorder` 호출이 `repository.save()` **커밋 이후**였다. append 가 실패하면 세션만
   남고 감사 기록이 비는 창이 생긴다
3. `/judge` 는 `JUDGED` 상태에서도 200 을 반환한다. 세 번 부르면 `appendGate` 가 세 번 쌓인다

## 결정

### 1. 적재 지점 — `core/EvidenceRecorder` 인터페이스, `evidence/` 구현

`core` 는 `evidence` 를 모른다. 데모 범위에 이벤트 인프라를 새로 들이지 않는다.

```java
void appendJudgment(String sessionId, Judgment judgment, int reverifyCount, Instant at);
void appendGate(String sessionId, GateResult result, Instant at);
```

> **이후 시그니처가 늘었다** (결정 자체는 그대로다 — 적재 지점과 인터페이스 위치).
> 판정을 만든 값이 가변 테이블에만 남는 문제(이슈 #136)로 두 인자가 붙었다.
>
> ```java
> void appendJudgment(String sessionId, Judgment judgment, int reverifyCount,
>                     String askedQuestion, QuestionSource questionSource, Instant at);
> ```
>
> `askedQuestion` 은 채점에 넘긴 문면(#137), `questionSource` 는 고객이 그것을 봤는지다.
> 둘 다 append-only 기록의 봉투 층이고 `Judgment` 계약에는 들어가지 않는다.

`recordJudgment` 와 `judge` 끝에서 호출하고, **덮어쓰기 전 값이 아니라 매 건** 적재한다.
구현 등록 전에도 세션 루프가 돌아야 하므로 `Optional` 주입 + `NO_OP` 기본값.

### 2. 트랜잭션 경계 — 세션 저장과 같은 트랜잭션

append 가 실패하면 요청 전체가 실패한다.

근거는 저장소의 성질에서 나온다. append-only 해시 체인은 **순서가 해시에 들어간다.** 구멍이
나면 나중에 끼워 넣을 수 없고 그 뒤 전체 체인의 검증이 깨진다. 재시도·보정으로 메꾸는 것은
체인을 다시 쓰는 것과 같아서 append-only 가 아니게 된다.

그리고 "세션은 있는데 감사 기록이 없다"는 상태가 F-CMN-002 가 존재하는 이유 그 자체다. 반대
방향도 같다 — append 는 됐는데 세션 저장이 실패하면 **존재하지 않는 판정의 기록**이 남는다.

논리가 P4 와 같다. **근거 없는 판정이 무효라면 기록 없는 판정도 무효다.** append 실패로 판정이
막히는 것은 게이트의 성격에 맞는 실패다.

**따라서 append 를 실패하지 않게 만드는 것이 `evidence` 소유자의 책임이다.** 해시 계산은 순수
함수로 두고 저장은 같은 H2 트랜잭션 안에서 한다. **적재 경로에 외부 I/O 를 넣지 않는다.**
별도 저장소로 나가야 할 이유가 생기면 그때 이 경계를 다시 정한다.

### 3. 중복 적재 — 흡수하지 않는다

`evidence` 는 오는 대로 전부 적재한다. "이건 같은 판정이다"를 판단하는 순간 저장이 아니라
정책이 되고, append-only 저장소가 정책을 가지면 **감사 기록을 저장소가 편집**한다는 뜻이 된다.
그리고 `/judge` 가 세 번 불린 사실 자체가 감사 정보다 — 실수인지 재계산 시도인지 나중에
물어볼 수 있어야 한다.

리포트는 마지막 것을 정본으로 쓴다. 중복이 있었다는 사실은 감사 로그에 남는다.

**서버 쪽은 별개로 멱등하게 막는 것을 권고한다**(`judgedAt` 이 있으면 재계산 없이 기록값 반환).
근거는 PR #16 합의 — *감사 기준점은 재계산값이 아니라 기록값*. 두 번째 호출이 재계산하면 그
사이 `gate_rules.yaml` 이 바뀌었을 때 다른 답이 나와 기준점이 둘이 된다. 이중 방어이고, 어느
쪽이 실패해도 기록은 사라지지 않는다.

### 4. 재설명 이력은 항목 판정 이력에서 복원한다

`SessionFsm` 상 `JUDGED` 에서 나가는 전이는 `CLOSE` 뿐이고 재설명 루프는
`IN_PROGRESS → RE_EXPLAIN → RE_VERIFY` 로 **판정 전에** 돈다. 따라서 정상 흐름의 게이트 판정은
1회이며, "처음에 황색이었다"는 게이트 이력이 아니라 **`appendJudgment` 이력**에서 복원한다.

### 5. 리포트에 신호등 색을 저장하지 않는다

리포트가 싣는 것은 `grade` 원값 · `evidence` · `contentHash` 다. 색은 렌더링이고 판정은
`GateResult.signal` 하나가 소유한다(P1). 색을 저장하면 **표시 관례가 바뀔 때 해시가 달라진다** —
같은 판정의 리포트가 다른 해시를 갖게 되면 교차 검증이 무너진다.

같은 이유로 항목별 신호등을 서버가 응답에 싣는 것도 반대한다(이슈 #39 (2번)). 게이트 판정이 항목
단위와 세션 단위 두 곳에 생기면 둘이 어긋날 때 어느 것이 판정인지 정할 근거가 없다.

### 6. `/judge` 는 조회와 확정을 겸하지 않는다

기획서 7-2 [기능 1]은 *"**황색 판정** → 재설명 → 재검증 → 녹색"* 인데, 판매자가 황색을 보려면
`/judge` 를 불러야 하고 부르면 `JUDGED` 라서 재설명으로 돌아올 수 없다. 오준서가 같은 곳을
다른 방향에서 짚었다(이슈 #39 (4번) — *"버튼 더블클릭 한 번이 세션을 끝낸다"*).

원인은 **`/judge` 가 조회와 확정을 겸하는 것**이다. 부수효과 없는 조회 경로를 분리한다.

```
GET  /sessions/{id}/gate-preview    기록하지 않는다. recorded=false
POST /sessions/{id}/judge           기준점 확정. 멱등(judgedAt 있으면 기록값 반환)
```

`GateEngine` 이 순수 함수라 자연스럽고, 이 분리가 있으면 위 3번의 중복 적재가 정상 흐름이
되지 않는다. **`JUDGED → REQUEST_REEXPLAIN` 전이를 여는 방식은 채택하지 않았다** — 판정 시점이
여러 개가 되면 "기준점은 기록값"(PR #16) 합의가 무너진다.

응답에 `recorded` 를 싣는다. **미리보기를 확정으로 오인하는 것을 막는 것이 이 필드의
목적이다.** 판정 후 미리보기는 재계산하지 않고 기록값을 준다 — 멱등과 같은 이유다.

`POST /judge` 에 **판정 0건 가드**를 함께 둔다. fail-closed RED 자체는 P5 에 맞지만 `JUDGED` 는
`CLOSE` 외에 나가는 전이가 없어 되돌릴 수 없다. 답변 하나 없는 세션이 버튼 오작동으로 끝나면
안 된다 → 409. 신호만 보려면 `gate-preview` 를 쓴다.

### 7. 항목별 신호등은 서버가 싣지 않는다

세션 신호등은 `gate-preview`·`judge` 가, 항목 등급은 `/sessions/{id}/judgments` 가 `grade`
원값으로 준다. **두 층으로 갈라 그린다.** 서버가 항목별 `signal` 을 실으면 게이트 판정이 항목
단위와 세션 단위 두 곳에 생기고, 둘이 어긋날 때 어느 것이 판정인지 정할 근거가 없어진다
(이슈 #39 (2번)).

## 결과

- `evidence` 구현자는 적재 경로에 외부 I/O 를 넣을 수 없다(트랜잭션 안에서 실패하면 안 되므로).
- 재설명 이력이 리포트에 남고, 7-2 [기능 1]의 황색→녹색 전이를 증거로 제시할 수 있다.
- 감사 기록이 세션보다 적은 상태가 생기지 않는다.
- 리포트 해시가 표시 관례 변경에 영향받지 않는다.
- 기획서 7-2 [기능 1]이 FSM 상 실제로 돈다. PR #28 이 그 흐름을 회귀 테스트로 고정했다 —
  `U3 → preview YELLOW(recorded=false) → re-explain → U1 → preview GREEN → judge GREEN`.
  미리보기가 없으면 두 번째 화살표에서 막힌다.
