# ADR-008. `CanonicalJson` 은 RFC 8785 를 따르고, 정규화는 직렬화기가 하지 않는다

- **상태**: Accepted
- **일자**: 2026-08-25
- **결정자**: 정세현
- **관련**: F-GTE-004, F-CMN-002, [ADR-003](003-evidence-ownership.md), [ADR-004](004-evidence-append-contract.md), PR #16, PR #22, `docs/decision-log.md` 10.2

## 맥락

`evidence/CanonicalJson` javadoc 이 **"결정해야 할 것" 6개**를 달고 있었다(PR #22). 그중
컬렉션 순서(`itemId` 정렬)는 ADR-004 가 정했고 다섯 개가 남았다.

- 객체 키 정렬 기준
- 숫자 표기
- 문자열 이스케이프 · 유니코드 정규화
- 타임스탬프 정밀도 · UTC
- null 필드 생략 여부

이 다섯 개는 **8/27 구현 착수 때 정하기로** 미뤄져 있었는데, 결정 자체는 코드가 없어도 할 수
있고 미뤄두면 착수일에 결정과 구현을 동시에 하게 된다. 그러면 결정이 구현 편의로 기울고,
`ADR-003` 이 이 클래스를 한 벌만 두려고 한 이유(*"여기서 갈라지면 감사 시점까지 안 보인다"*)가
약해진다. 그래서 착수 전에 정한다.

## 판단 기준

두 가지를 놓고 정했다.

**① 외부에서 검증 가능한가.** `contentHash` 의 용도는 *"이 기록은 위조되지 않았다"* 를 보이는
것이다(`decision-law` 5.11). 감사자가 **우리 코드 없이** 같은 해시를 재계산할 수 있어야 그
주장이 성립한다. 그러려면 우리 고유 규칙을 만들지 말고 표준을 따라야 한다. 그래서 기본값은
**RFC 8785 (JCS) 그대로**다.

**② 논리적으로 같은 내용이 항상 같은 바이트인가.** 표준이 열어둔 지점만 우리가 닫는다.

## 결정

### 1. 키 정렬 — UTF-16 코드유닛 순서 (RFC 8785 그대로)

Java `String.compareTo()` 가 정확히 그 순서다. 별도 comparator 를 만들지 않는다.

코드포인트 순서를 고르면 보조평면 문자(이모지 등)가 키에 들어갈 때 결과가 갈린다. 우리 키는
ASCII + 한글이라 **실질 차이가 없지만**, 차이가 없는 지점에서 표준을 벗어날 이유도 없다.
벗어나면 그 사실을 문서로 알아야만 검증할 수 있는 해시가 된다.

### 2. 숫자 — RFC 8785(ECMAScript 최단 왕복 표기). 단 해시 대상에 부동소수를 넣지 않는다

- 정수는 지수 표기 없이 그대로. `-0` 은 `0` 으로
- `NaN` · `Infinity` 는 **직렬화를 거부한다**(예외). JSON 에 표현이 없고, 감사 기록에 표현
  불가능한 값이 들어가서는 안 된다
- **해시 대상 payload 에 `double`·`float` 를 담지 않는다.** 금액은 원 단위 `long`, 비율은
  `BigDecimal` 로 소수 자릿수를 고정한다

세 번째가 이 절의 실질이다. 부동소수는 계산 경로가 조금만 달라져도 마지막 자리가 흔들리고,
그 순간 **같은 판정이 다른 해시를 낸다.** P2(시뮬레이터 결정론)와 같은 논리이고, 여기서는
결과가 더 나쁘다 — 시뮬레이터는 숫자가 달라지는 데서 끝나지만 해시 체인은 **그 뒤 전체가
검증 실패**가 된다.

리포트가 싣는 것이 `grade` 원값 · `evidence` · `contentHash` 뿐이라(ADR-004 §5) 지금 당장
부동소수가 들어올 자리는 없다. 이 규약은 나중에 누가 넣으려 할 때를 위한 것이다.

### 3. 문자열 — 최소 이스케이프. **정규화는 직렬화기가 하지 않는다**

이스케이프는 RFC 8785 그대로 — JSON 이 요구하는 것(`"` · `\` · U+0020 미만 제어문자)만,
정의된 짧은 형태를 쓰고 인쇄 가능한 문자를 `\uXXXX` 로 바꾸지 않는다.

**NFC 정규화는 `CanonicalJson` 안에서 하지 않는다.** RFC 8785 도 유니코드 정규화를 범위 밖으로
둔다. 대신 **입력 경계에서 NFC 를 강제하고 그것을 테스트로 못박는다.**

이유가 P3·P4 와 같다. 직렬화기가 정규화하면 **직렬화가 내용을 바꾼다.** 그러면 저장된
`utteranceQuote` 와 해시 대상이 달라지고, `verify_quote_is_verbatim`(ai-service)이 원문과
대조하는 그 문자열이 어느 쪽인지 모호해진다. 화면이 PII 를 미리 마스킹하면 안 되는 이유
(*"화면이 조용히 본문을 바꾸면 근거가 원발화와 달라진다"*)와 정확히 같은 구조다.

경계는 이미 NFC 다 — `ai-service/app/parsing.py` 가 `pages[].text` 를 NFC 로 내고
`scripts/make_parsing_samples.py` 도 NFC 로 대조한다. 없던 것은 **서버 진입점**이라 그쪽에
넣는다.

### 4. 타임스탬프 — UTC 강제, 밀리초 3자리 고정

```
2026-08-25T09:34:16.000Z
```

- 오프셋 표기를 쓰지 않는다. `+09:00` 과 `Z` 는 같은 시각인데 다른 바이트다
- `Instant` 를 `truncatedTo(ChronoUnit.MILLIS)` 로 자르고 **3자리를 항상 채운다.**
  `.0Z` · `.000Z` · `.000000Z` 가 갈리면 안 된다

`Instant.now()` 의 정밀도가 플랫폼에 따라 다르다(밀리초 ~ 나노초). 자릿수만 다른 같은 시각이
다른 해시를 내는 것을 막는 게 이 절의 목적이다.

밀리초로 충분한 이유 — **적재 순서는 타임스탬프가 아니라 해시 체인(`prev_hash`)이 정한다.**
같은 밀리초에 두 건이 들어와도 순서는 체인에 남는다. 정밀도를 올릴 이유가 없다.

### 5. null 필드 — 유지한다. 생략하지 않는다

생략하면 **"값이 null"과 "필드가 없음"이 같은 바이트**가 된다. 계약이 nullable 로 둔 필드에서
실제로 갈린다.

가장 분명한 예가 히트맵이다(`decision-log` 5.6).

```json
{"item": "...", "misrate": null, "n": 12, "masked": true}
```

`misrate: null` 은 **소표본 마스킹이 동작했다는 증거**다. 셀을 지우지 않고 null 로 내리기로 한
이유가 그거였는데, 직렬화가 null 을 생략하면 **그 증거가 해시에서 사라진다.** 리포트 요약본의
`downloadUrl`(nullable)도 같다.

## 결과

- `contentHash` 를 **RFC 8785 구현이 있는 아무 언어로도** 재계산할 수 있다. 감사자가 우리 코드를
  신뢰하지 않아도 검증된다
- 표준이 열어둔 네 지점(부동소수 금지 · 정규화 위치 · 타임스탬프 자릿수 · null 유지)만 우리가
  닫았고, 닫은 이유가 문서에 있다
- `evidence/CanonicalJson` javadoc 의 "결정해야 할 것" 목록을 이 ADR 참조로 바꾼다. 두 곳에
  적으면 갈린다
- **8/27 착수 시 결정이 아니라 구현만 남는다**

## 남은 것

`CanonicalJson.serialize()` · `bytes()` 구현과, 위 3번이 요구하는 **서버 진입점의 NFC 강제**가
남았다. 둘 다 8/27~8/29 evidence 공통 기반 작업이다(이슈 #54).

RFC 8785 를 직접 구현할지 검증된 JCS 라이브러리를 쓸지는 구현 판단으로 남긴다 — 어느 쪽이든
이 ADR 의 결정은 바뀌지 않는다. 다만 라이브러리를 쓰면 **위 2·4·5 가 그 라이브러리에서도
성립하는지 테스트로 확인**해야 한다. 특히 null 유지는 JSON 라이브러리 기본값이 반대인 경우가
흔하다.
