# 결정 로그 — PR·이슈에서 확정된 것 전수

소유: 정세현 (`docs/`) · 각 항목의 결정자는 표에 적었다

## 어디까지 훑었나

**기준은 번호가 아니라 시각이다.**

| 훑은 날 | 이 시각까지의 본문·리뷰·코멘트를 다 읽었다 | 옮긴 PR |
|---|---|---|
| 2026-08-25 | `2026-08-25T13:00:00Z` | #52 |
| 2026-08-26 | `2026-08-26T02:02:00Z` | #74 |
| 2026-08-26 (보강) | `2026-08-26T03:00:00Z` — #74 리뷰 대조 + PR #81 결정 반영 | #74 |

번호 범위(`#1~#52` 같은)로 적으면 **이미 훑은 PR·이슈에 나중에 달린 코멘트를 못 잡는다.**
번호는 *그 항목이 존재했다*만 말하고 *그 뒤로 무슨 말이 오갔는지*는 말하지 않는다.

이번에 실제로 그랬다 — 이슈 **#37 · #41** 은 8/25 훑기 범위 안이었는데, 8/26 01:39 에 배포
형태·`data/` 마운트·자격증명 방식이 **한꺼번에 확정됐다**(7.11~7.16). "번호 #53 부터" 로만
봤으면 인프라 확정 전부를 놓쳤다.

다음 훑기는 위 시각부터 이렇게 시작한다.

```bash
gh search prs    --repo sphinx-fin/sphinx --updated ">=2026-08-26T02:02:00Z" --limit 60 \
  --json number,title,updatedAt
gh search issues --repo sphinx-fin/sphinx --updated ">=2026-08-26T02:02:00Z" --limit 60 \
  --json number,title,updatedAt
```

걸린 항목은 **번호가 낮아도 다시 열어본다.** 이 문서에 없는 것이 *결정되지 않은 것*인지
*아직 안 옮긴 것*인지는 이 표가 가른다.

## 왜 이 문서가 있나

PR 스레드에서 합의된 것이 **코드에는 반영됐지만 레포에 근거가 없는** 경우가 반복됐다. ADR
004~007 이 그중 원칙급 4건을 옮겼지만, 그건 *한 세션에서 관여한 것 위주*였고 전수가 아니었다.
이 문서가 그 전수다 — 위 표의 범위에 든 PR·이슈의 본문·리뷰·인라인 코멘트를 전부 훑었다.

**용도는 두 가지다.**

1. 코멘트를 놓친 사람이 여기 한 곳만 보면 자기 영역에서 무엇이 확정됐는지 안다
2. 다음 사람이 이미 정해진 것을 다시 정하거나 반대로 구현하는 것을 막는다

## ADR 과의 관계

| | 무엇 | 어디 |
|---|---|---|
| ADR | 원칙급 결정. 뒤집으려면 새 ADR 이 필요한 것 | `docs/adr/` |
| **이 문서** | 확정된 것 전수 색인. 세부 계약·규약·배선 결정 포함 | 여기 |

ADR 에 있는 것은 **번호만 가리키고 본문을 복제하지 않는다.** 두 벌이 되면 갈린다 —
`CanonicalJson` 이 정규화를 한 벌만 두는 것과 같은 이유다.

**이 문서는 결정을 만들지 않는다.** 전부 PR·이슈에서 이미 합의된 것이고, 출처 열이 그 근거다.
사실과 다르면 말해달라 — 남의 결정을 내가 이해한 대로 적은 것이 많다.

| 10.2.1 | **NFC 입력 경계가 어디인가** — ADR-008 이 *"직렬화기가 아니라 입력 경계에서"* 까지만 정하고 위치는 구현 판단으로 남겨뒀다. 윤지석 질문(#55 리뷰)으로 확정한다. **① Spring 은 NFC 를 보장하지 않는다** — `new String(bytes, UTF_8)` 도 Jackson 역직렬화도 유니코드 정규화를 하지 않고 들어온 코드포인트를 그대로 들고 있다. **② 정본 경계는 Spring 요청 진입점**이다(ADR-008 초안이 후보로 적은 *"`PiiGateway.mask()` 직후"* 를 이쪽으로 좁힌다). 근거는 해시 대상이 무엇인가에 있다 — 세션은 발화 원문을 저장하지 않고(`Session` 에 그 필드가 없다) 해시에 들어가는 것은 `Judgment.Evidence.utteranceQuote` 인데, **그건 ai-service 가 본 텍스트에서 잘라낸 것**이다. 상류에서 형태를 고정하면 인용도 해시도 따라온다. 거꾸로 `/internal/*` 입구를 경계로 잡으면 Spring 상태만 NFD 로 남는다. **③ ai-service 는 2차 방어선으로 남기되 동작이 PII 와 반대다** — PII 는 걸리면 **거부**(마스킹하면 상류 P3 위반이 조용히 덮인다), NFC 는 걸려도 **정규화하고 진행**(거부하면 정답 발화가 채점 자체를 못 받는다. 자판 문제지 고객 잘못이 아니다). **④ NFC 이고 NFKC 가 아니다** — NFKC 는 전각 `７`→`7` 까지 접어서 마스킹이 보는 내용을 바꾸고, 그러면 마스킹 결과가 정규화 위치에 의존한다. 윤지석의 `scoring._canonical()` (#56)은 **저장이 아니라 대조**라 ADR-008 3번과 충돌하지 않는다 — 다만 상류가 형태를 보장하기 전까지는 조합형 인용이 대조를 통과한 뒤 그대로 해시되므로, ②가 ③보다 먼저다. 그때까지 `_canonical()` 이 유일한 방어선이라 **지우면 안 된다**. **남은 것은 삽입 지점 한 가지** — 요청 DTO 역직렬화 직후냐 `mask()` 래퍼냐. #67 이 `PiiGateway.mask()` 를 `AiServiceClient.score()` 안으로 넣으면서 고객 텍스트가 나가는 단일 지점이 코드로 생겼으므로 후자가 유력하다. **ADR-008 은 고치지 않는다** — 결정이 아니라 구현 판단으로 남겨둔 부분을 좁힌 것이다 **삽입 지점 확정(강희진, #71 리뷰): `AiServiceClient.score()` 안, `PiiGateway.mask()` 와 같은 줄.** `Normalizer.normalize(answerText, Form.NFC)` 를 먼저 하고 그 결과를 `mask()` 에 넘긴다 — **순서는 정규화 → 마스킹**이다. 반대로 하면 마스킹 판정 이후에 남은 원문 부분의 형태가 바뀌는 모양이 되므로, 판정과 저장 형태를 같은 입력에 맞춘다. 요청 DTO 역직렬화 직후가 아니라 경계 안쪽인 이유는 #67 이 마스킹을 클라이언트 경계 안에 둔 것과 같다 — 밖에 두면 *"정규화를 잊지 않기"* 에 기대게 되고 새 엔드포인트마다 그 자리를 다시 만들어야 한다. ⚠️ **조건**: 그러면 경계가 엄밀히는 "Spring 요청 진입점"이 아니라 "ai-service 로 나가는 경계"다. 지금은 차이가 없다 — `Session` 이 발화 원문을 저장하지 않기 때문이다(강희진 확인). **Spring 안에 원문을 저장하게 되는 변경이 생기면 그때 정규화를 요청 진입점으로 올려야 한다.** 그 조건이 이 결정의 유효 범위다. | 정세현 · 강희진(지점 합의) | **결정 완료**(지점 포함) · 구현은 8/27 | #55 리뷰 · #56 `95268ec` · #67 |
